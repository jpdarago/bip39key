# Generate an OpenPGP/OpenSSH/age key from a BIP39 mnemonic

> the `--algorithm` flag, they were created with `xor`. To ensure you can always
> regenerate them, pass `--algorithm xor` explicitly. New keys should use
> `--algorithm hkdf`.

> 1.12.0 can fail to decrypt with keys bip39key generates, reporting
> `Bad secret key`. Your key is fine. See [Known issues](#known-issues).

> :information_source: If you reimplement bip39key's derivation or check its output
> with other tools, read [Known bugs](#known-bugs) first: `-r` and Electrum seeds
> do not do exactly what their names suggest.

Generates a cryptographical key from a [BIP39](https://github.com/bitcoin/bips/blob/master/bip-0039.mediawiki) mnemonic (and, optionally, a
passphrase).

It can generate either

* An OpenPGP EdDSA signing key + ECCDH encryption key, both using Curve25519.
* An OpenPGP EdDSA signing key with Curve25519.
* An OpenSSH key using EdDSA with Curve25519.
* An [age](https://age-encryption.org) X25519 identity. See [age keys](#age-keys).

In all cases the tool requires a User ID in [RFC 2822](https://datatracker.ietf.org/doc/html/rfc2822) format.

When providing a passphrase, the tool will use it to generate the key together
with the seed from the BIP39 mnemonic and the user id, and will also encrypt the 
resulting OpenPGP/OpenSSH keys with the provided passphrase.

The creation timestamp for the OpenPGP keys is set to the Bitcoin genesis block
timestamp (1231006505 in seconds from Unix epoch). GPG considers this part of
the key so it is important to keep it consistent. We use that timestamp because
it's easy to retrieve, and it's not zero (which can trigger bad corner cases in
GPG).

## age keys

`--format age` writes an [age](https://age-encryption.org) identity file, and
`--format age --public-key` writes the matching `age1...` recipient, as
`age-keygen -y` would print it:

```
$ bip39key -u "User <user@email.com>" --algorithm hkdf -f age -o key.txt
$ bip39key -u "User <user@email.com>" --algorithm hkdf -f age -k
age1...
$ age -r age1... secret.txt > secret.txt.age
$ age -d -i key.txt secret.txt.age
```

age output requires `--algorithm hkdf`. The age key is derived with its own
HKDF info string (`bip39key-age-v1`), so it is independent of the OpenPGP
encryption subkey from the same seed: leaking one does not leak the other. The
`xor` and `concat` algorithms cannot derive a separate key, so they are
rejected with age output.

Unlike the OpenPGP and SSH output, **the age identity is always written in
plaintext**. age identity files have no passphrase protection, so a passphrase
only feeds key derivation. Protect the file accordingly; bip39key creates it
with mode 0600. The identity file also has no `# created:` line, so that the
output is deterministic.

The OpenPGP-only flags (`-a`, `-j`, `-b`, `-d`, `-y`, `--auth-subkey`) and `-n` are
rejected with age output.

## Why BIP39

[BIP39](https://github.com/bitcoin/bips/blob/master/bip-0039.mediawiki) is a
mnemonic code for the generation of deterministic wallets for Bitcoin and other
cryptocurrencies. This format consists of a few words (up to 24) from a special
dictionary that contains no ambiguous characters or words than can be
confused with each other. It also includes a checksum to ensure that it
was backed up properly.

Using a BIP39 mnemonic instead of a passphrase allows for easier, safer backups
(because of the checksum and dictionary design) and ensures a consistent amount
of entropy is provided. A passphrase's entropy depends on the algorithm used
to generate the passphrase, and the passphrase length. Too short a passphrase
can make the resulting key weak.

## Wordlist source

The binary bundles the BIP39 english wordlist, available in the repo in [resources/bip39.txt](`https://github.com/jpdarago/bip39key/blob/main/resources/bip39.txt`).

If you want to override the wordlist, you can use the env var `WORDLIST_BIP39`.

IMPORTANT: It must be in the same format as the one above (one word per line).

## Entropy source

The BIP39 seed is expanded from 128/256 bits to 512 bits using Argon2id, with
the User ID as the salt.

Optionally, you can provide a passphrase. The `--algorithm` flag controls how
the seed and passphrase are combined:

* **`xor`** (current default) — Applies Argon2id separately to the seed and
  passphrase, then XORs the results.
* **`concat`** — Concatenates the seed and passphrase, applies Argon2id, and
  splits the output at a fixed offset into sign and encrypt keys.
* **`hkdf`** (recommended for new keys) — Concatenates the seed and passphrase,
  applies Argon2id, then uses HKDF-Expand (RFC 5869) with distinct info strings
  (`bip39key-sign-v1` and `bip39key-encrypt-v1`, plus `bip39key-age-v1` for age
  output) to derive independent sign and encrypt keys. This provides proper domain separation between key types.

The passphrase is also used to encrypt the OpenPGP and SSH files themselves. If
you want to keep that encryption but not use the passphrase as additional entropy,
then pass the `--skip-passphrase-for-key-material/-n` option.

> :warning: The `xor` algorithm has a weakness: if an attacker obtains your
> passphrase and output key, they can recover the hashed seed via XOR and
> attempt to brute force the input phrase. While this is very difficult due to
> 128 bits of entropy and Argon2id's computational cost, both `concat` and
> `hkdf` avoid this issue entirely.

## Installing shell completions and manpage

Building the project generates shell completions and a manpage automatically
(in `completions/` and `man/`). Below are instructions for installing them.

### NixOS

If you package bip39key in a Nix derivation, add the completions and manpage
to the install phase:

```nix
postInstall = ''
  installShellCompletion --bash completions/bip39key.bash
  installShellCompletion --zsh completions/bip39key.zsh
  installManPage man/bip39key.1
'';
```

For a standalone install without a derivation:

```bash
# Bash
cp completions/bip39key.bash ~/.local/share/bash-completion/completions/bip39key

# Zsh
cp completions/bip39key.zsh ~/.local/share/zsh/site-functions/_bip39key

# Manpage
sudo cp man/bip39key.1 /run/current-system/sw/share/man/man1/
# Or add to your home-manager or NixOS configuration instead.
```

### Debian/Ubuntu

```bash
# Bash
sudo cp completions/bip39key.bash /usr/share/bash-completion/completions/bip39key

# Zsh
sudo cp completions/bip39key.zsh /usr/share/zsh/vendor-completions/_bip39key

# Manpage
sudo cp man/bip39key.1 /usr/local/share/man/man1/
sudo mandb
```

### macOS

```bash
# Bash (requires bash-completion from Homebrew)
cp completions/bip39key.bash $(brew --prefix)/etc/bash_completion.d/bip39key

# Zsh
cp completions/bip39key.zsh $(brew --prefix)/share/zsh/site-functions/_bip39key

# Manpage
cp man/bip39key.1 /usr/local/share/man/man1/
```

## Known bugs

None of these changes the key a given seed produces, and most can never be
fixed for that reason: fixing them would give every existing user a different
key. Apart from the `xor` weakness at the end, they do not affect the security
of your keys. They matter mainly if you reimplement bip39key's derivation, or
check its output with other tools.

### `--use-rfc9106-settings` uses 1 lane, not 4

`-r/--use-rfc9106-settings` takes its Argon2id parameters from the
[rust-argon2](https://crates.io/crates/rust-argon2) crate's
`Config::rfc9106()`. That is 2 GiB of memory and 1 pass, as in RFC 9106's first
recommended option, but **1 lane**, where the RFC recommends 4. The number of
lanes changes Argon2id's output, so a tool set to the RFC's recommendation
derives a different key from the same inputs.

Keys made with `-r` have always used 1 lane, so it stays that way. To reproduce
bip39key's derivation elsewhere, use these Argon2id (v1.3) parameters, with the
user ID as the salt and a 64-byte output:

| Settings | Memory | Passes | Lanes |
|---|---|---|---|
| Default | 64 MiB (65536 KiB) | 32 | 8 |
| `-r/--use-rfc9106-settings` | 2 GiB (2097152 KiB) | 1 | 1 |

### Electrum seeds are not Electrum's seed

With `--seed-format electrum`, bip39key turns the phrase into 32 bytes of
entropy with PBKDF2-HMAC-SHA512 and 2048 iterations, like Electrum. Electrum
uses the text `electrum` as the salt. bip39key was meant to do the same but
instead uses the six bytes you get by base64-*decoding* `electrum`
(`7a 57 9c b6 bb a6`). So the entropy bip39key starts from is not the
first 32 bytes of Electrum's own seed for that phrase.

Your keys are unaffected: they are still a deterministic function of the
phrase, and the result only feeds Argon2id. It matters if you reimplement the
derivation, which needs that 6-byte salt. Related limitations:

* bip39key does not use Electrum's seed extension (its passphrase). Use
  bip39key's own `--passphrase` instead.
* Only Electrum's `standard` and `segwit` seed types are accepted; `2fa` and
  pre-2.0 seeds are rejected.

### Uneven base64 lines in armored and OpenSSH output (fixed in 1.9.0)

Up to 1.8.2, bip39key broke the base64 in armored OpenPGP keys (`-a`) and
OpenSSH private keys (`-f ssh`) at uneven points instead of every 64 or 70
characters. GnuPG and `ssh-keygen` accept that, but strict parsers do not: for
example, Rust's [`ssh-key`](https://crates.io/crates/ssh-key) crate rejects
those OpenSSH keys with `InvalidEncoding`.

The key inside is identical, so 1.9.0 and later regenerate exactly the same
key, just laid out differently; only a byte-for-byte comparison of the files
will differ. To fix an OpenSSH key file made by an older version without
regenerating it, have `ssh-keygen` rewrite it (enter the same passphrase twice
to keep it, or press Enter for none):

```bash
ssh-keygen -p -f path/to/key
```

### `-n` wrote unencrypted key files (fixed in 1.9.1)

Up to 1.9.0, `-n/--skip-passphrase-for-key-material` dropped the passphrase
entirely: it stayed out of key derivation, as intended, but the OpenPGP or
OpenSSH secret key file was also written **unencrypted**, contrary to the
option's description. The derived key was always correct. If you created a key
file with `-n` and a passphrase, treat that file as unprotected: regenerate it
with a fixed version, or encrypt it with `gpg --edit-key ... passwd` or
`ssh-keygen -p -f path/to/key`.

### `-i` was ignored in a terminal (fixed in 1.9.2)

Up to 1.9.1, `-i/--input-filename` only worked when standard input was not a
terminal, for example in a script or a pipe. Run from a terminal, bip39key
prompted for the seed phrase and never read the file. No wrong key was ever
produced: the key came from whatever was typed at the prompt.

### The `xor` algorithm leaks more than it should

The default `--algorithm xor` lets someone who has both your passphrase and
your key recover the Argon2id hash of your seed. See the warning under
[Entropy source](#entropy-source). Use `--algorithm hkdf` for new keys.

## Known issues

These are bugs in other software that affect bip39key users.

### `Bad secret key` with libgcrypt 1.12.0 (Ubuntu 26.04)

libgcrypt 1.12.0 has a bug in its elliptic-curve code (upstream
[T8094](https://dev.gnupg.org/T8094), fixed in 1.12.1). Before decrypting,
gpg-agent asks libgcrypt to check that the secret key matches the public key,
and 1.12.0 wrongly rejects about half of all valid Curve25519 keys. Decryption
then fails with:

```
gpg: public key decryption failed: Bad secret key
```

The key bip39key generated is correct, and the same seed keeps producing the
same key. [Sequoia](https://sequoia-pgp.org/), and GnuPG with every other
libgcrypt version we tested (1.11.3, 1.12.1, 1.12.4), decrypt with it. Whether a particular key hits
the bug depends on its value, not on how you exported it: adding a passphrase
does **not** avoid it.

To check whether you are affected, look at the libgcrypt line in:

```bash
gpg --version
```

If it says `libgcrypt 1.12.0`, decrypt on a system with a different version
until your distribution ships 1.12.1 or later. Ubuntu 26.04 currently ships
1.12.0; Ubuntu 24.04 and macOS (Homebrew) do not. OpenSSH keys are unaffected,
since OpenSSH does not use libgcrypt.

## Running tests

The suite has two layers. Unit and property tests live inside the library and
run in milliseconds; integration tests exercise the binary end-to-end against
GPG, ssh-keygen and age, and require `gpg`, `ssh-keygen` and `age` to be
installed.

```bash
cargo test --release                     # everything
cargo test --release --lib               # unit and property tests only (fast)
cargo test --release --test integration  # integration tests only
```

If using [Nix](https://nixos.org/) with [devenv](https://devenv.sh), you can also run `devenv test`.

Integration tests include golden vectors in `test/golden/`, which pin the exact
bytes produced for each combination of flags. A diff there means the key derived
from a given seed phrase has changed, which breaks every existing user — treat it
as a breaking change, not a failing test to update.
